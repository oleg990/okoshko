# Архитектура

## Принципы

1. **Код разложен по фичам**, а не по техническим слоям: всё про записи лежит в `booking`, всё про вход в `auth`.
2. **Внутри фичи слои**: модель и бизнес-логика, хранилище, HTTP. Бизнес-логика не знает ни про PostgreSQL, ни про HTTP.
3. **Интерфейс описывает тот, кто его использует.** Пакет объявляет маленький интерфейс того, что ему нужно от соседа, а сосед удовлетворяет ему неявно. Поэтому фичи не импортируют друг друга по кругу.
4. **Всё собирается в одном месте**: `cmd/api/main.go` создаёт реализации и передаёт их туда, где они нужны.
5. **Время приходит через интерфейс `Clock`**, а не из `time.Now()` в логике. Иначе напоминания и истечение запросов не протестировать.

## Фичи (пакеты)

| Пакет | За что отвечает | Таблицы |
|---|---|---|
| `auth` | аккаунты, способы входа, одноразовые токены, выдача сессии, проверка ролей | `accounts`, `auth_identities`, `one_time_tokens` |
| `performer` | профиль мастера (slug, описание, аватар, часовой пояс, режим подтверждения, шаг записи) и его услуги | `performers`, `services` |
| `schedule` | недельный шаблон и исключения (выходные, больничный), рабочие окна на диапазон дат | `working_hours`, `schedule_exceptions` |
| `availability` | расчёт свободного времени: чистая функция без БД | нет |
| `booking` | записи, клиенты мастера, статусы и история, токен управления записью, подтверждение, отклонение, отмена, истечение запросов | `bookings`, `booking_status_history`, `clients` |
| `notification` | каналы уведомлений, запланированные уведомления, воркер отправки, отправитель Telegram | `notification_channels`, `scheduled_notifications` |
| `admin` (позже) | список мастеров, блокировка | использует `auth` |

Клиенты пока живут внутри `booking`: они создаются только при записи, а отдельная карточка клиента появится в v0.2. Когда разрастутся, выделим в `client`.

### Где живёт расчёт свободного времени

Отдельный пакет `availability`, внутри чистая функция:

`Calculate(рабочие окна, занятые интервалы, длительность + буфер, шаг) → список начал записи`

Ей нужны данные из `schedule` и `booking`, но она их не импортирует. Она объявляет два маленьких интерфейса:
- `WorkingWindows(performerID, from, to)`: рабочие окна в UTC, их реализует `schedule`.
- `BusyIntervals(performerID, from, to)`: занятые интервалы, их реализует `booking`.

`booking` при создании записи вызывает `availability`, чтобы проверить, что время вообще предлагалось. Зависимости идут в одну сторону: `booking → availability`, а `schedule` и `booking` подставляются в `availability` в `main.go`. Цикла нет.

## Двойная запись: путь ошибки

Гарантию даёт ограничение в БД, а не код.

1. Две клиентки одновременно вставляют пересекающиеся записи.
2. PostgreSQL принимает одну, второй возвращает ошибку с SQLSTATE `23P01` (`exclusion_violation`).
3. **Только `booking/postgres`** знает про `pgconn.PgError`. Он проверяет код и возвращает доменную ошибку `booking.ErrSlotTaken`.
4. Сервис пробрасывает её дальше, оборачивая через `%w`.
5. HTTP-слой проверяет `errors.Is(err, booking.ErrSlotTaken)` и отвечает `409 Conflict` с кодом `slot_taken`.

Проверка «свободно ли» перед вставкой в сервисе остаётся, но как оптимизация: быстрый понятный отказ без обращения к ограничению. Истина всё равно в БД.

Похожим образом: `23505` (`unique_violation`) превращается в `ErrAlreadyExists`, запись не найдена превращается в `ErrNotFound`.

### Внутри каждой фичи (на примере `booking`)

```
booking/
├── model.go         # Booking, Client, статусы
├── errors.go        # ErrSlotTaken, ErrNotFound, ...
├── repository.go    # интерфейс Repository (что нужно сервису от хранилища)
├── service.go       # бизнес-логика
├── service_test.go
├── postgres/        # реализация Repository на PostgreSQL
├── memory/          # реализация для быстрых тестов
└── httpapi/         # HTTP-обработчики, DTO, роуты
```

Модель, ошибки и интерфейсы лежат в корне фичи, а не в подпапках `repository` и `service`. Так подпакеты (`postgres`, `httpapi`) импортируют корень фичи, а он их не импортирует, и циклов не возникает.

## Слои и правила импорта

- `httpapi` знает про `service` и про `model`. Про БД не знает.
- `service` знает про интерфейс `Repository` и про `Clock`. Про HTTP и `pgx` не знает.
- `postgres` знает про `pgx` и про `model`. Про HTTP не знает.
- Фичи не импортируют конкретные реализации друг друга. Нужно что-то от соседа: объявляй интерфейс у себя.
- Только `main.go` знает обо всех сразу.

## Фоновые задачи

В MVP воркер уведомлений работает горутиной внутри того же процесса. Раз в минуту он берёт из `scheduled_notifications` записи со статусом `pending` и `send_at <= now` и отправляет их. Там же истекают запросы подтверждения по `confirm_until`. Остановка через `context` (graceful shutdown). Если нагрузка вырастет, воркер выносится в отдельный бинарник `cmd/worker` без переписывания логики.

## Открытые вопросы

- Название проекта и путь модуля (`github.com/<ник>/<проект>`).
- Роутер: `chi` или стандартный `net/http` с маршрутизацией из Go 1.22+.
- Формат сессии мастера после входа через Telegram: JWT или серверная сессия в БД.
